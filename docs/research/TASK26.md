## 정책 문제의 공식화

**주어진 것**: 세션 집합과 각 세션의 turn 계획(segment 길이, 생성 길이, tool gap). substrate는 [TASK16](TASK16.md)의 descriptor로 기술된다.

**결정 변수**: 세션 *i* 마다 `hold_i ∈ [0, ε]`. 세션이 tool을 마친 시점에서 `hold_i` 만큼 반환을 늦춘다. **작업량은 바꾸지 않는다** — segment 길이도 생성 길이도 그대로다.

**불변량**: decode 작업은 보존된다. 계획이 생산할 token 수를 고정하므로 어떤 일정에서도 `Σ actual`(decode step에 걸친 실제 요청 수의 합)이 같다. 모든 평가에서 이 불변량을 assert하며 위반 시 실패한다.

**평가 축** (넷을 동시에 본다)

| 축 | 정의 |
|---|---|
| device time | `Σ step_time(actual)` + `Σ prefill_s`. **유일한 비용 축** |
| utilization | `Σ actual / Σ bucket`. 무차원 slot 점유율 |
| 층 2 재사용 | resume 요청 중 hit 개수 |
| p99 추가 지연 | baseline 대비 **요청별 완료 시각 증가분**의 p99 (hold 값이 아니다) |

**핵심 회계**: 작업량이 보존되므로 일정이 바꾸는 것은 **각 token이 타고 가는 batch의 폭**이다. padding된 넓은 batch는 token당 비용이 좁은 batch보다 싸다 — [TASK13](TASK13.md) 값으로 bucket 1은 token당 9.87 ms, bucket 8은 1.62 ms다. **따라서 device time과 slot 점유율은 반대로 움직일 수 있고, 비용은 device time뿐이다.**

### 관측 2 — 이득의 원천 분해

device time 변화는 **집중(concentration)** 과 **재계산(recompute)** 의 합과 정확히 같다(항등식이며 잔차가 아니다). 집중은 token이 더 높은 동시성 수준으로 옮겨 가면서 생기는 decode 시간 변화이고, 재계산은 prefill 시간 변화다.

| N | ε=1 s 집중 / 재계산 | 비중 | ε=5 s 집중 / 재계산 | 비중 |
|---|---|---|---|---|
| 6 | −2.419 / −0.223 s | **91.6 % / 8.4 %** | −8.003 / −0.317 s | **96.2 % / 3.8 %** |
| 8 | −2.118 / −0.581 s | 78.5 % / 21.5 % | −4.099 / −0.560 s | 88.0 % / 12.0 % |
| 10 | −1.225 / −0.424 s | 74.3 % / 25.7 % | −4.422 / −1.448 s | 75.3 % / 24.7 % |
| 12 | −0.347 / −0.802 s | **30.2 % / 69.8 %** | −1.676 / −2.234 s | **42.9 % / 57.1 %** |

**N이 커질수록 지렛대가 batching에서 cache 생존으로 넘어간다.** N=6에서는 이득의 96 %가 집중이고, N=12에서는 57 %가 재계산 절감이다.

**선등록 지시문이 지목한 세 원천 중 "padding 감소"는 원천이 아니었다.** N=6 ε=5 s에서 device time이 27 % 줄었는데 padding slot은 **562개 늘었다.** 정지 군집화(`stall_s`)도 같은 조건에서 4.34 → 4.81 s로 **늘었다.** 이득은 세 축 어느 것도 아닌 **동시성 집중**에서 나왔다.

## 핵심 발견

1. **`class`(형태) + `stack`(값) — utilization은 비용 지표가 아니다.** 작업량이 보존되는 재배치에서 utilization과 device time은 반대로 움직일 수 있고 실제로 움직인다. utilization을 최대화한 일정이 device time을 11–37 % 더 쓰고(관측 3), 실측 arm 비교에서도 방향이 5/11 어긋난다(관측 4). 형태를 `class`로 보는 근거: 이산 batch 크기 집합에 올림하는 어느 substrate에서나 "넓고 padding된 batch가 token당 싸다"가 성립하므로, 점유율과 비용의 괴리는 이 구현의 성질이 아니다.
2. **`stack` — 반환 시점 재배치에는 실질적 headroom이 있다.** ε = 0.5 s에 1.2–4.4 %, ε = 5 s에 9.7–27.2 %다. 이 값은 국소 탐색의 결과이므로 **하한**이다.
3. **`stack` — 지렛대는 N에 따라 갈린다.** N=6에서 이득의 96 %가 동시성 집중이고 N=12에서는 57 %가 재계산 절감이다. **낮은 동시성에서는 batching이, 높은 동시성에서는 cache 생존이 정책의 대상이다.**
4. **`universal` — 사전에 지목한 원천 셋이 모두 빗나갈 수 있다.** 지시문은 padding 감소 / 재사용 증가 / 정지 군집화를 원천 후보로 지목했는데, 최대 이득 구간에서 padding은 **늘고** 정지도 **늘었다.** 원천은 넷째 축(동시성 집중)이었다. **분해 축을 사전에 고정하되 항등식으로 닫아 두면, 빗나갔다는 사실 자체가 관측이 된다.**
5. **`stack` — agentic gap의 device-time 비용은 utilization이 보여 준 것보다 훨씬 크고 부호가 뒤집히지 않는다.** [TASK20](TASK20.md)–[TASK25](TASK25.md)의 "부호가 바뀐다"는 결과는 **utilization 축의 사실**이며, device time 축에서는 11/11 전부 AGENTIC이 비싸다.

## 해석

- **(해석)** 발견 5는 [TASK20](TASK20.md)–[TASK25](TASK25.md)를 반증하지 않는다. 그 TASK들은 utilization ratio를 재겠다고 선언하고 그것을 쟀으며 값은 재현·예측까지 됐다. 바뀌는 것은 **그 결과가 정책에 대해 무엇을 허가하는가**다. "N=6에서 agentic이 15 % 낫다"는 slot 점유율의 문장이지 비용의 문장이 아니다.
- **(해석)** 그렇다고 utilization이 쓸모없는 것은 아니다. 두 arm의 **작업 타이밍이 고정된** 비교에서는 여전히 padding 구조를 드러내는 지표이고, [TASK23](TASK23.md)의 격자 개입은 utilization 축에서 인과가 확인됐다. **문제는 그것을 목적함수로 쓸 때다.**
- **(해석)** ε = 0.5 s에 4 % 남짓이라는 값은 정책 설계를 정당화하기에 충분해 보인다. tool 호출 사이의 0.5초 지연은 agentic 응용에서 사용자에게 거의 보이지 않는 크기이고, 그 대가가 device time 4 %면 교환비가 유리하다. 다만 **online 정책이 offline 값을 낼 수 있다는 근거는 없다.**
- **(해석)** N=10·12의 값은 [TASK25](TASK25.md)가 검증한 범위 밖이다. 방향(이득이 있다, N이 클수록 재계산 비중이 크다)은 기전과 정합하지만 **크기는 검증되지 않았다.**

## 실패 / 무효 시도

- **처음 분해에서 decode 시간 변화를 "padding 감소"로 이름 붙였다.** N=6 ε=5 s에서 padding slot이 562개 **늘었는데도** decode 시간이 8 s 줄어드는 것을 보고 이름이 틀렸음을 알았다. `Σ actual`이 보존된다는 항등식으로 다시 세워 "동시성 집중"으로 고쳤다. **집계 부호만 보고 채널 이름을 붙이면 정반대 해석이 나온다.**
- **초기 oracle이 hold 값 자체의 p99를 "추가 지연"으로 보고했다.** 실제로 필요한 것은 baseline 대비 **완료 시각**의 증가분이다(hold가 0인 세션도 남의 hold 때문에 늦어질 수 있다). 요청별 완료 시각 차이로 교체했다.

## 연구 원칙에 미치는 영향

1. **점유율(utilization)을 비용으로 읽지 않는다.** 작업량이 보존되는 비교에서 점유율과 device time은 반대로 갈 수 있다. 정책의 목적함수는 device time이다.
2. **기존 결론을 새 축에서 다시 읽되, 원래 결론을 소급해 부정하지 않는다.** [TASK20](TASK20.md)–[TASK25](TASK25.md)는 utilization을 재겠다고 하고 쟀다. 바뀐 것은 허가 범위다.
3. **원천 분해는 잔차가 아니라 항등식으로 닫는다.** 그래야 사전에 지목한 축이 전부 빗나갔다는 것이 관측이 된다.
4. **offline oracle의 값을 online 정책의 목표로 옮기지 않는다.** 전지적 계산은 상한의 성격이고, 국소 탐색이라 하한이기도 하다 — 두 방향을 함께 적는다.
5. **검증되지 않은 구간의 계산 결과는 방향과 크기를 분리해 보고한다.**
