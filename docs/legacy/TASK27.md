### 1-1 근거가 되는 세 축과 그 셀

### 1-2 도출된 KEEP 규칙 (v0) — **확정 (사용자 승인 2026-08-07)**

> **KEEP 조건: `L > ~905 tok` **AND** `예상 도구시간 < 2 s` **AND** `GPU KV 압박 낮음`**
> 셋 중 하나라도 어긋나면 **KEEP 하지 않는다**(기존 동작 유지).

**★ 조건별 지위가 다르다 — 같은 무게로 인용하지 말 것:**

| 지위 | 조건 | 성격 |
|---|---|---|
| **몸통 (강증거)** | `L > ~905 tok` **AND** `도구시간 < 2 s` | TASK08 4셀·TASK09 5셀에서 **부호 반전 + 단조/계단**이 관측됐고 후자는 **코드 상수와 일치**. 규칙의 실체는 이 둘이다 |
| **가드 (외삽·보수 장치)** | `GPU KV 압박 낮음` | **실측 임계가 아니다.** [TASK07](TASK07.md) 의 F1(hit↑인데 latency↑)이 큰 L 에서도 재현되는 것을 **막기 위한 보수적 차단기**일 뿐이다. **임계는 S-B 가 채운다**(§3) |

**각주 (v0 의 보수성)**: `2 s` 경계는 **게이트 절벽에서 유래**한 값이다 — 즉
`FIXED_THRESHOLD_CONTINUUM=2.0` 이 pin 을 차단하기 시작하는 **관측 범위의 경계**이지
"KEEP 이 손해로 바뀌는 지점"이 아니다. **KEEP 의 진짜 손익 경계는 2 s 보다 클 수 있다**
(pin 이 걸리기만 하면 더 긴 도구 시간에도 이득일 여지). v0 는 그 불확실성을
**KEEP 을 과소 적용하는 쪽**으로 처리한 **보수적 선택**이다.

각 조건의 근거 셀과 **신뢰도**:

| 조건 | 근거 | 셀 수 | 신뢰도 |
|---|---|---|---|
| `L > 905` | TASK08 4레벨, 경계에서 부호 반전 + 그 위 단조 | 4 | **높음** — 부호 반전과 단조가 같은 방향 |
| `tool < 2 s` | TASK09 5레벨, 계단형 + `pin=0` 기전 확인 | 5 | **높음** — 코드 상수(`FIXED_THRESHOLD_CONTINUUM=2.0`)와 일치 |
| `압박 낮음` | TASK07(1.0x) vs TASK08 p150(2x) | **2** | **★ 낮음 — §1-3** |

### 1-3 ⚠️ 정직하게 — 압박 조건이 가장 약한 다리다

1. **셀이 2개뿐**이고 그중 하나(TASK07)는 **JOBS 도 다르다**(8 vs 4). 압박은 "풀 크기 × 동시성"
   묶음이라 **단일 축으로 분리되지 않았다**.
2. **★ 결정적 공백 — 압박 변화를 큰 L 에서 재지 않았다.** 두 압박 점은 전부 **prompt ≈ 405**
   (KEEP 이득이 없는 영역)에서 비교됐다. 정작 **KEEP 이득이 큰 L(1705~3305)에서 압박을 올리면
   어떻게 되는지는 데이터가 없다.**
   → 규칙의 세 번째 조건은 **작은 L 에서 관측한 것을 큰 L 로 외삽**한 것이다.
   3단계 A/B 가 이 공백을 정면으로 시험한다(시나리오 2 = 압박 높음).
3. 압박 임계값을 **수치로 못 박을 수 없다** — 1.0x/2x 두 점뿐이라 "낮음"의 경계가 미정.
   → 3단계는 임계를 **탐색 대상**으로 두고, 우선 두 끝(여유/빡빡)만 대조한다.

## 2. 2단계 — 압박 신호 조사 (**결론: 새 계측 불필요**)

### 2-1 신호 2(`cpu_state`)는 쓸 수 없다
[TASK19](TASK19.md) 의 신호 2 는 **CPU DRAM 계층 점유율**(offload 목적지가 찼는가)이다.
KEEP 이 필요로 하는 것은 **GPU KV 풀 점유율**(블록을 붙잡아도 되는가)로 **다른 자원**이다.
→ 재사용 불가. 사용자 예상대로다.

### 2-2 ★ 기존 카운터로 충분하다 — `kv_cache_manager.usage`

| 항목 | 내용 |
|---|---|
| 위치 | `vllm/v1/core/kv_cache_manager.py:133` — `@property usage` |
| 구현 | `block_pool.get_usage()` = `1.0 − free_blocks/(total−1)` (`block_pool.py:318`) |
| 비용 | **O(1)** — `free_block_queue.num_free_blocks` 는 속성 조회, 나눗셈 1회 |
| 범위 | `[0.0, 1.0]` — 그대로 "압박" 지표 |
| **이미 쓰이는가** | **예** — `scheduler.py:1407` 이 `SchedulerStats.kv_cache_usage` 로 읽고 있다 |
| 훅에서 접근 | **가능** — `on_step` 훅이 `scheduler.py:794`, 같은 객체 안 |

→ **새 회계를 만들 필요가 없다.** 이미 있는 값을 **한 줄 더 읽어** 신호에 싣기만 하면 된다.
[TASK19](TASK19.md) 신호 2 가 스케줄러에서 lmcache 통계를 못 읽어 **자체 회계(C3)** 를 만들어야
했던 것과 대조적이다 — 이번엔 그 문제가 없다.

**read-only 원칙 준수**: 값을 읽기만 하고 아무것도 바꾸지 않는다. 훅 본문은 여전히
스칼라 저장뿐(I/O·락 없음).

### 2-3 제안하는 최소 변경

```
scheduler.py  : on_step(...) 인자에 kv_cache_manager.usage 추가        (1줄)
continuum_signal.py : 스칼라 필드 kv_usage 저장 + 샘플에 포함          (3줄)
```
결정기 3-way 확장(`decide()` 에 KEEP 후보 추가)은 **규칙 검토 후** 착수한다 —
`decide()` 는 `replay_check` 40/40 과 회귀 테스트가 걸려 있어 신중해야 한다.

## 2-4 ★ 주입 지점을 보고 발견한 것 — **v0 는 기존 게이트의 "제한"이다**

3단계 설계 전에 실제 주입 지점을 읽었다. `estimate_with_func.py:150` 의 `set_up_pin` 은
**10줄**이고 이것이 전부다:

```python
def set_up_pin(self, request):
    if request.this_func_call is None: return 0
    t = self.get_func_call_exec_time(request.this_func_call) or 0.0
    if t > FIXED_THRESHOLD_CONTINUUM: return 0      # ← 유일한 게이트
    return FIXED_THRESHOLD_CONTINUUM                 # ← pin TTL
```

**기존 게이트는 `L` 도 `압박` 도 보지 않는다.** 도구시간만 본다.
그러므로 우리 v0 규칙(`L>905 AND tool<2s AND 압박낮음`)은 기존 동작에 대해
**순수한 제한(restriction)** 이다 — 기존이 pin 하던 것 중 일부를 **안 하게** 만든다.

| 조건 | KEEP-off (기존) | KEEP-on (v0) | 규칙의 값 |
|---|---|---|---|
| 긴 L + 짧은 도구 + **여유** | pin | pin | **동일 — 차이 없음** |
| 작은 L + 짧은 도구 | pin | **안 함** | TASK08 p150 Δ+0.023 → 이득 미미 |
| 긴 L + 짧은 도구 + **압박 높음** | pin | **안 함** | TASK07 Δ**+0.16** → **여기가 값** |
| 도구 > 2 s | 안 함 | 안 함 | 동일 |

### ⚠️ 그래서 S-A 는 "KEEP 이 이기는 시나리오"가 될 수 없다
승인해 주신 S-A(긴 문맥 + 짧은 도구 + **여유 압박**)는 **양쪽 팔이 똑같이 pin** 하므로
**M5 의 GATE-only 처럼 붕괴**한다. 이건 하네스 문제가 아니라 **v0 규칙의 성질**이다.

**정정 제안**: S-A 의 역할을 **"이겨야 할 시나리오" → "무해성 확인(붕괴 예상)"** 으로
바꾸고, **실질 시험은 S-B 하나**로 둔다. 붕괴 자체를 결정 로그로 확인·보고한다
(M5 R1 · GATE-only 처리와 같은 규칙).

### ★ "헤지 논리가 적응 편" 예측이 실제로 사는 자리는 따로 있다
그 예측이 성립하려면 규칙이 **기존이 안 하던 pin 을 하게** 만들어야 한다.
그 자리는 **긴 L + 도구시간이 2 s 를 조금 넘는 구간**이다 — 재획득 비용이 `L` 에 비례해
크므로 pin 이 여전히 이득일 수 있는데, 기존 게이트는 **일률적으로 차단**한다(TASK09 pin=0).
§1-2 각주가 말한 "**진짜 손익 경계는 2 s 보다 클 수 있다**"가 바로 이 지점이다.

**다만 v0 는 그 확장을 하지 않는다**(보수적 선택, 사용자 확정). 확장 팔(`KEEP-ext`,

| 시나리오 | BLOCKS | kv_usage 중앙 | >0.7 비율 | n_running | n_waiting |

**의미론을 검증하지 않았다** — 값이 존재한다는 것과 그 값이 원하는 양이라는 것은 다르다.

#### ★★ 왜 빡빡에서 이득이 안 났나 — **F1 구간에 도달하지 못했다**
