## 1. (a) 팔 전환 메커니즘 — **런타임 토글 가능하나, 이 실험에서는 쓰면 안 된다**

### 1-1 env 는 재시작 필요

| 변수 | 읽는 시점 | 런타임 변경 |
|---|---|---|
| `CONTINUUM_POLICY` | `ContinuumPolicy.__init__` (스케줄러 생성 시) 1회 — `continuum_policy.py:92` | ❌ |
| `CONTINUUM_KEEP` | `keep_enabled()` 가 **프로세스당 1회** 캐시 — `continuum_policy.py:379-388` | ❌ |
| `CONTINUUM_SIGNAL` | `__init__` (kill switch, 최상위) | ❌ |

### 1-2 그런데 **요청별 오버라이드가 env 를 이긴다**

| 축 | 필드 | 값 | 코드 |
|---|---|---|---|
| EVICT/OFFLOAD | `kv_transfer_params["continuum.arm"]` | `off` / `recompute` / `offload` / `gate` / `adapt` | `continuum_policy.py:268` |
| KEEP(pin) | `kv_transfer_params["continuum.keep"]` | `on` / `off` / `forced` / `denied` | `estimate_with_func.py:167-189` |

**단서**: `continuum.arm` 은 서버가 `CONTINUUM_POLICY≠off` 로 떠 있어야만 읽힌다
(`apply()` 가 `self.enabled` 에서 즉시 반환 — `continuum_policy.py:249`).
즉 요청별 팔을 쓰려면 서버를 `adapt` 로 띄우고 요청마다 팔을 실어야 한다.

### 1-3 판정 — **블록 = 서버 인스턴스로 확정** (스펙 기본 가정 그대로)

기술적으로는 한 인스턴스에서 세 팔을 교차할 수 있다. **그러나 용량 실험에서는 금지다.**
팔들이 **공유 자원**(GPU KV 풀, lmcache CPU 계층, NVMe 대역)을 통해 서로를 오염시키므로,
섞으면 "그 팔의 용량"이 아니라 **혼합의 용량**을 재게 된다. M7 에서 요청별 교차가
옳았던 이유(세션 효과 회피)는 **슬라이스 지연**을 쟀기 때문이고, 용량은 반대다.

**다만 요청별 필드를 팔 무결성 assert 에 활용한다**: env 로 팔을 세우고 **동시에**
모든 요청에 같은 팔을 명시적으로 실어, 결정 로그의 `arm` 필드로 이중 확인한다
(환경변수 미적용 사고 방지 — 스펙의 팔 무결성 게이트를 코드 레벨로 강화).

## 2. (b) NVMe 쓰기 누적 — **통과, 여유 8배 이상**

### 2-1 KV 크기 (모델 config 실측 유도)

`Llama-3.1-8B`: 32층 × 8 KV헤드 × head_dim 128 × 2(K,V) × 2B(bf16)
= **131,072 B = 128 KiB / token**

| L | 세션 문맥 KV |
|---|---|
| 1024 | 128 MiB |
| 8192 | **1 GiB** |

### 2-2 블록당 쓰기 추정 (S=32, 측정창 4분)

lmcache 는 청크 단위 저장이라 **턴마다 문맥 전체를 다시 쓰지 않는다** — 세션 첫 턴에
문맥 전체, 이후는 증분(대화가 턴당 ~50~100 tok 성장)만 기록된다.

```
초기 저장  : 32 세션 × 평균 L 4608 tok × 128 KiB   ≈  18 GiB
증분 저장  : 32 × ~80 턴 × ~100 tok × 128 KiB      ≈  33 GiB
재축출·재저장 여유 (×3 보수)                        ≈ 150 GiB  ← 상한으로 채택
```

### 2-3 예산 판정

```
예상 쓰기(상한)  150 GiB
여유             1.7 TiB (= 1740 GiB, /mnt/nvme 실측)
예산 = 여유×0.7  1218 GiB
150 < 1218  →  ✅ 통과 (여유 8.1배)
```

블록마다 캐시 디렉토리를 초기화하므로 **공간은 블록 단위로 회수**된다(누적 아님).
30블록 누적 쓰기는 1.5~4.5 TiB — 공간 문제는 없고, 1.8 TB NVMe 내구성 대비
**0.4~0.8% 수준**이라 무시 가능하나 기록해 둔다.

**구현**: [TASK26](TASK26.md) 의 `preflight_budget()` 패턴을 그대로 이식하되,
상수를 이 워크로드 기준(위 식)으로 바꾸고 **블록마다** `df` 로 여유를 재확인한다
(디렉토리 초기화 실패를 조용히 넘기지 않기 위해).

## 3. (c) 블록당 재개 이벤트 수 — **n≥40 은 여유롭게 충족, 위험은 반대쪽**

프리필 처리량을 무부하 재계산 실측(`RECOMPUTE_NOLOAD`: L1024 147.2 ms · L8192 1274.7 ms)
에서 유도하면 **≈ 6,400 tok/s**. 평균 L 4608 tok.

| 체제 | 가정 | 블록당(4분) 재개 이벤트 |
|---|---|---|
| **전부 미스**(프리필 바운드, 최악) | 6400 / 4608 ≈ 1.39 turn/s | **≈ 330** |
| **전부 히트**(디코드 바운드) | 서비스시간 급감 | 수백~1000+ |
| **S=4**(저부하) | 세션당 주기 ~2.9 s | 4 × 83 ≈ **330** |

**어느 체제·어느 S 에서도 블록당 수백 이벤트**로 문턱 40 을 크게 넘는다.
셀당 n = 2블록 × 수백 = **500+**. 워밍업 폐기(세션당 첫 재개 1회 = S개)는 무시 가능.

→ **n≥40 assert 는 통과 예상.** 그래도 **fail-loud 로 유지**한다(조용한 통과 금지 원칙).
실제 위험은 반대쪽 — 이벤트가 **너무 많아** 쓰기·시간이 늘어나는 쪽이고, 그건 §2 에서 확인됐다.

**시간 수지**(로그 실측 기반): 서버 기동 ~50 s + 워밍업 60 s + 측정창 240 s + 종료 ~10 s
≈ **6 분/블록** → 30블록 **≈ 3 h**. 스펙 추정과 일치. 게이트·기준선·분석 별도.

## 4. ⚠️ 스펙대로 가면 측정이 무의미해지는 결함 — Δ1~Δ3

### Δ1. **L 혼합은 턴별이 아니라 세션별이어야 한다** (치명)

스펙: "세션 1개 = 루프: [프리필(L ~ 혼합분포) → 도구 대기 → 재개] 반복" — 턴마다 L 추출로 읽힌다.

**근거**: 하네스의 대화는 **누적**이고(`continuum_client.py:67,86,110`), `L` 을 만드는 것은
**첫 user 메시지의 `--pad-tokens`** 다(`:73,79-80`). 즉 **`L` 은 세션의 속성**이고,
그 패딩 prefix 가 바로 pin/offload/재계산의 대상이다.

**턴마다 L 을 새로 뽑으면** 턴마다 프롬프트가 완전히 새 것이 되어 **prefix 재사용이 0** 이 된다
— KEEP 도 OFFLOAD 도 **잴 대상 자체가 사라진다**.

**대안(내가 확정 가능)**: `L` 은 **세션 시작 시 1회** 추출 `{1024:50%, 8192:50%}`.
턴마다는 대화가 자연히 ~50~100 tok 자란다. "프롬프트 유니크"는 **세션 간** 요건으로 해석
(`ctx{job_index}` 패딩이 이미 그 목적 — `:71-73` 주석이 명시).

### Δ2. **tool_s 를 명령어 정체성에 묶어야 한다** (치명)

**근거**: 게이트가 보는 값은 요청의 실제 대기시간이 아니라
**`func_call_to_exec_time[func]` = 명령어별 전역 평균**이다(`estimate_with_func.py:130-146`).

스펙대로 턴마다 tool_s 를 `{0.5, 1.5, 3.0}` 에서 독립 추출하면서 명령어를 순환시키면,
**모든 명령어의 평균이 혼합 평균 1.15 s 로 수렴**한다 → `1.15 < 2.0` →
**"3.0 s 가 게이트를 막는" 사건이 영원히 일어나지 않는다.** 도구시간 축이 통째로 죽는다.

**대안(내가 확정 가능)**: 명령어 ↔ tool_s **1:1 고정**
(`ls`=0.5 s / `pwd`=1.5 s / `date`=3.0 s), 턴마다 **명령어를** `{50%, 30%, 20%}` 로 추출.
그러면 명령어별 평균이 각 수준으로 수렴해 게이트가 의도대로 갈린다.

**추가 함정**: 명령어의 **첫 관측은 이력이 없어 `None`** 이고 호출부가 `or 0.0` 으로
받으므로(`:154`) **0.0 < 2.0 → 게이트 통과**한다. 워밍업에서 **각 명령어를 최소 1회씩
소진**시켜야 한다(스펙의 "세션 첫 재개 1회 폐기"만으로는 부족 — 명령어 3종 기준).

### Δ3. ★ **이 L 혼합에서 KEEP 규칙은 공집합 → P4 를 검정할 수 없다** (사용자 결정 필요)

`KEEP_MIN_L = 905`, `KEEP_MAX_TOOL_S = 2.0` (`decision.py:114-115`).
L 혼합 `{1024, 8192}` 은 **둘 다 905 초과** → `keep_check` 가 **한 번도 막지 않는다**.
바깥 게이트가 이미 `tool_s > 2.0` 을 걸러내므로 도구시간 조건도 추가로 막을 게 없다.

→ **ADAPT(KEEP=on) 와 gate-only 의 pin 집합이 완전히 동일하다.**
두 팔의 차이는 **전부 offload 축**에서만 나오고,
**P4 의 메커니즘 서사("pin 이 풀을 잠식")는 이 설계로 검정되지 않는다.**

**대안 2 안 — 결정 필요**

| 안 | 내용 | 대가 |
|---|---|---|
| **(i)** L 혼합에 **905 미만 성분 추가** (예: `{512:25%, 1024:37.5%, 8192:37.5%}`) | KEEP 이 실제로 pin 을 제한 → **P4 검정 가능** | M5 대비쌍 `{1024, 8192}` 과의 정합이 느슨해짐 |
| **(ii)** **P4 를 재정의** — gate-only vs static-OFF 로 "offload 정책 일반의 용량 가치"만 재고, pin 잠식 서사는 뺀다 | 격자 불변 | **F1 메커니즘의 용량판**이라는 P4 의 논문 내 역할이 사라짐 |

**내 추천 = (i)**. P4 가 경제 서사에서 지고 있는 무게(=F1 을 용량 축으로 옮기는 다리)가
대비쌍 정합보다 크다. 다만 **격자 변경은 사용자 승인 사항**이라 대기한다.

## 5. 하네스 개조·정의 모호 — Δ4~Δ6

### Δ4. **현 클라이언트로는 "첫 토큰까지"를 못 잰다** (개조 필요, 내가 확정 가능)

`post_chat` 은 **비스트리밍**이라 `latency` 는 **응답 완료까지**(디코드 32 토큰 포함)다
(`continuum_client.py:39-51`). 스펙의 주 지표 "도구 완료 → **첫 토큰**"을 재려면
`stream: true` + 첫 청크 수신 시각 기록이 필요하다.
개조하지 않으면 지표에 **디코드 잡음이 섞여** 재개 비용이 희석된다.

### Δ5. **SLO 기준선이 이봉의 중앙값이라 불안정** (설계 보정 제안)

L 혼합 50/50 이면 재개지연 분포가 **이봉**이다(무부하 재계산 기준 L1024 ≈ 147 ms vs
L8192 ≈ 1275 ms, 8.7배). 그 **중앙값은 두 모드 사이에서 흔들리고 `n` 에 의존**한다 —
방법론 규칙 D-2·D-3(이봉·`n` 병기)이 경고한 바로 그 상황이다.
`S=1, n=60` 의 중앙값을 SLO 기준선으로 쓰면 **기준선 자체가 흔들린다.**

**대안**: SLO 와 주 지표를 **L 층화**로 간다(L 별 기준선 → L 별 SLO → money graph 2패널).
어차피 **"오선택 비용 ∝ L"** 이 논문의 축이므로, L 을 접는 것은 서사와도 어긋난다.

### Δ6. **"gate-only(순정 기본값)" 의 정의가 갈린다** (사용자 결정 필요)

| 읽기 | 구성 | 결과 |
|---|---|---|
| **(A)** 진짜 순정 | lmcache **미설정** — offload 계층 없음. pin + 재계산만 | 세 팔이 뚜렷이 다름. **P4 의 "offload 정책 일반의 용량 가치"가 성립** |
| **(B)** 정책만 off | lmcache 설정 + `arm=off` → `skip_save` 미주입 → lmcache **기본(저장)** | **gate-only ≈ static-OFF** 로 붕괴 — 팔 3개가 실질 2개가 된다 |

**추천 = (A)**. (B) 면 실험이 2팔짜리가 된다.
단 (A) 는 **서버 구성 자체가 달라지는 팔**이라 교란이 크다는 점을 한계로 명시해야 한다.

**이름 충돌 주의**: [TASK25](TASK25.md) 의 `GATE-only` 는 **다른 것**이다
(= `continuum.arm=gate`, 무부하 지도로 고정한 정적 결정기). 논문·로그에서 혼동 금지 —
이번 팔은 `stock-gate` 같은 다른 이름을 권한다.

| **Δ6** | gate-only = **lmcache 미설정** | assert = lmcache 프로세스 부재 + offload 0건. **서사 2층 구조**(계층의 가치 / 적응의 증분) 명시 |
| **Δ5** | L 층화 + **자 통일** | `SLO_L = 2 × p95(S=1 기준선, L별)`. 헤드라인 = **min-over-L 최대 S**. 기준선 팔 간 p95 불일치 시 fail-loud |
| **풀** | **override 57,344 tok(3,584 블록) 확정** | + **자연 풀 앵커**(215k, S=32 × 3팔 × 1블록, 예측 "동치"). 기준선도 override 풀에서 — 자 통일 |

### 8-1 풀 결정의 근거 (내가 계산해 올린 것)

자연 풀 **215,104 tok** 에서 S=32 수요는 `8×512 + 12×1024 + 12×8192 = 114,688 tok`
= **53%**. 즉 자연 풀에서는 **메모리 축이 아예 포화하지 않아** 곡선이 순수 계산 대기만
재게 된다. override 로 S=16 에서 수요≈풀, S=32 에서 2배 압박이 되도록 정규화했다.

### 8-2 ★ P 구조 개편 (사용자 지시)

내가 올린 정량 문제: **재정의된 P4 의 회수 지렛대가 작다.** ADAPT 가 pin 을 거부하는
대상은 `L=512` 인데 그건 **가장 작은 문맥**이라 회수량이 override 풀 기준
`4,096 / 57,344 = 7.1%` 뿐이다. 이것은 KEEP 규칙("작은 L 은 재계산이 싸니 pin 안 함")의
**구조적 귀결**이지 구현 문제가 아니다. 반면 **offload 는 멈춘 세션의 KV 를 전량 회수**한다.

→ 사용자 결정:

| | 내용 |
|---|---|
| **P4 강등** | 기본 예측 = **미검출**. 검출되면 **슬롯/단편화 효과로 등록하고 원인 표기**, **용량 회수로 주장 금지** |

### 12-2 헤드라인 — **세 팔의 용량이 같다**

| 팔 | L=512 | L=1024 | L=8192 | **헤드라인(min-over-L)** |
|---|---|---|---|---|
| gate-only | 16 | 8 | 8 | **8** |

S=4·8 에서는 세 팔 모두 **0.5~0.9× SLO** 로 여유롭고, S≥16 에서 **5~27× SLO** 로 붕괴한다.
곡선이 아니라 **절벽**이다.

### 12-3 ★ 절벽의 정체 — 팔이 아니라 **작업집합 / 풀**

S=16 셀은 같은 팔인데 블록마다 갈렸다(gate-only 0.090 s ↔ 2.353 s, **26배**;
static-OFF 1.227 s ↔ 0.108 s, **11배**). 풀링한 셀 값은 그래서 **무의미**했다.

원인은 **세션별 L 추첨이 블록마다 실현 작업집합을 바꾸기 때문**이다.
블록별 실현 작업집합(= 세션 재개 프롬프트 토큰의 합)을 풀로 정규화하면 완전히 갈린다:

```
생존 블록 (15개):  작업집합/풀 = 0.06 ~ 1.17×
붕괴 블록 (15개):  작업집합/풀 = 1.15 ~ 2.60×
                              ↑ 문턱 ≈ 1.0× (겹침 단 한 점)
```

**자연 풀 앵커가 이 규칙을 교차 검증한다**: S=32 인데도 작업집합이 0.48~0.59× 라
**세 팔 전부 생존**(1.27~1.55× SLO, 팔 간 동치) — 선등록 예측 그대로다.

즉 **용량을 정하는 것은 정책이 아니라 `작업집합 / GPU KV 풀` 하나**이고,
`S` 는 그 대리변수일 뿐이다(같은 S 에서도 추첨에 따라 0.76×~1.20× 로 흔들린다).

### 12-4 ★★ 가장 중요한 음성 결과 — **offload 는 용량을 사지 못한다**

`static-OFF` 와 `ADAPT` 는 결정의 **99.2%(16,891/17,022)를 OFFLOAD** 로 내렸고
계층은 **100% cpu** 였다. 그런데도 **offload 계층이 아예 없는 `gate-only` 와 같은
문턱에서 같이 무너진다.**

해석(기전): offload 는 KV 의 **사본 위치**를 바꿀 뿐, 재개 시점에 **GPU 로 다시 올려야 하는
양**을 줄이지 못한다. 작업집합이 풀을 넘으면 어느 팔이든 스래싱한다. 이는 Phase 1 의
자기간섭 발견(부하 하 reload 는 비싸다)과 **같은 방향**이다.
